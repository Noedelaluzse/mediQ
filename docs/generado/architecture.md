# Architecture (digest — source of truth: `docs/08-arquitectura.md`)

- Monorepo pnpm with `apps/mobile` (Expo + RN). **Backend = Firebase** (Auth, Firestore, Storage); there is no own API/PostgreSQL. Stack: `docs/07-stack-tecnico.md`.
- Four modules: auth, consultas, recetas, medicos. Each with 4 layers: `domain/` → `application/` → `infrastructure/` · `presentation/`.
- Dependency rules (enforced by `eslint-plugin-boundaries`):
  - `domain/` imports only `domain/` and `shared/kernel`.
  - `application/` imports only `domain/`.
  - `presentation/` imports `application/` and `shared/`, never `infrastructure/`.
  - Only `app/container.ts` (composition root) imports `infrastructure/`.
  - A module imports another only via its `index.ts`.
- Aggregates reference each other by id. Use `Result<T, DomainError>`, no exceptions for domain errors.
- Routes (Expo Router) live in `apps/mobile/src/app/routes` (`root` option in `app.json`); keep them thin. `app/container.ts` is the sibling composition root.
- Never edit `ios/` or `android/` (generated).
- Theme: `docs/09-tema-y-colores-intercambiables.md`. Auth: `docs/10-autenticacion-con-google.md`. Data model + security rules: `docs/11-modelo-de-datos-firestore.md`.
- Auth (F001): `modules/auth` has domain/application/infrastructure/presentation. Google and the API are SIMULATED adapters in `infrastructure/Simulated*` wired in `app/container.ts`; swap them for the real adapters (and add `POST /auth/google`) without touching domain or UI. Session lives in expo-secure-store.
- Current state: monorepo with only `apps/mobile`. Data access goes through ports (repositories); Firebase adapters live in `infrastructure/`. Security rules are the ONLY authorization layer: write and test them with the Firebase emulator (`firebase/`). Routes live in `apps/mobile/src/app/routes`. Template files with color literals are exempted in `eslint.config.mjs` (`LEGACY_COLOR_FILES`) until replaced.
- Médicos (F006–F008): `modules/medicos`. Lee `visits` solo por el puerto `ConsultasDeMedicosRepository` (el módulo de consultas, F009, será quien las escriba). **Selector de médico:** la pantalla `/medicos-elegir` guarda lo elegido en `presentation/seleccionDeMedico.ts` (tienda de un solo uso) y vuelve atrás; el formulario de consulta lo recibe con `useMedicoElegido(alElegir)`. Los chips "Usados antes" salen de `ListarLugaresUsadosAntes`. Los hooks que importan `expo-router` van en archivos aparte de la lógica pura para poder probarla en Vitest.
- Consultas (F009): `modules/consultas`. `Consulta` valida fecha no futura, tipo y especialidad del catálogo (`shared/kernel/especialidades.ts`, compartido con médicos) y próxima cita posterior. `RegistrarConsulta` primero valida todo y solo después asegura al médico y al lugar (puertos `MedicosParaConsulta` y `LugaresParaConsulta`, cuyos adaptadores en `infrastructure/adaptadoresDeMedicos.ts` usan el directorio de médicos: reutilizan por id o por nombre sin acentos/mayúsculas, o crean) y guarda en `visits`. Así el dominio de consultas no conoce el de médicos. La pantalla `/consulta-nueva` (opcional `?medicoId=`) usa `shared/ui/DateTimeField` (selector nativo `@react-native-community/datetimepicker`) y `useMedicoElegido`. La lógica del formulario (valores iniciales, tipo, médico elegido) vive en `presentation/formulario.ts`, pura y probada.
- Reglas de Firestore: `firebase/firestore.rules` enumera cada colección (las reglas se suman, un comodín anularía la validación de `visits`); detalle en `docs/11`. Se prueban con `pnpm --filter mobile test:emulator` y se publican a mano.
- Borrador (F010): `consultas/domain/Borrador` (+ `esBorradorVacio`) y el puerto `BorradorRepository`; casos de uso `GuardarBorrador` (si el formulario quedó vacío, borra), `RecuperarBorrador`, `DescartarBorrador`. `SqliteBorradorRepository` usa `expo-sqlite` a través de la interfaz `BaseSqlite` (para probarlo con una base falsa); `baseSqliteNativa.ts` es lo único que importa `expo-sqlite`. `EliminadorConBorradores` envuelve el borrado remoto de la cuenta y borra también el borrador local. La pantalla recupera al abrir, guarda con pausa de 800 ms **solo después de recuperar** (si no, el formulario vacío pisaría el borrador) y borra al guardar la consulta (`Cancelar` lo conserva).
- Indicaciones (F011): `Indicacion` (`id`, `texto`, `orden`, `hechaEn?`) vive en `consultas/domain`; `Consulta.indicaciones` es la lista marcable. **Ojo con los nombres:** `notasDelMedico` es el texto libre "¿Qué te dijo el médico?" (Firestore `doctorNotes`) e `indicaciones` es la lista. `RegistrarConsulta` valida los textos antes de tocar nada y `FirestoreConsultasRepository.guardar` escribe la consulta y sus `instructions` en un solo lote. Casos de uso para consultas ya guardadas (los usará el detalle, F015): `ListarIndicaciones`, `AgregarIndicacion`, `AlternarIndicacion` (marcar/desmarcar), `QuitarIndicacion`, sobre el puerto `IndicacionesRepository`.
- Diario (F013): `ConsultaDelDiario` y `agruparPorMes` (domain), puerto `DiarioRepository.pagina(cursor?)`, caso de uso `ListarDiario(previas, cursor?)` que suma la página nueva a lo ya mostrado y devuelve los grupos por mes. `FirestoreDiarioRepository` pagina con `orderBy('visitedAt','desc')` + `startAfter(último documento)` y filtra las borradas en el cliente; el cursor es opaco para el dominio. La pestaña Diario (`DiarioScreen`) recarga al enfocarse y carga más al llegar al final. Pendiente: abrir el detalle (F015), próxima cita arriba (F014), chip de receta y búsqueda (RF-17).
